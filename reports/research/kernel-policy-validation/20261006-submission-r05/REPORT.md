# R05：主机提交路径消融与模型维度探针

## 决策摘要

本批完成。小矩阵自定义内核收益并非全部由Python造成：16x64x64、64x128x1024、128x128x2048在C++普通提交下，两进程都支持V7超过5%的收益。
但图执行后，64x128x1024和128x128x2048没有稳定超过5%的赢家，32x128x256稳定偏向V4。不能将普通调用的静态规则直接推广到图模式。
新增两组Qwen2.5-1.5B来源维度探针，均未出现跨进程稳定的V7优势；图模式均为cuBLAS V4胜出。
这支持收紧测量/部署契约，不足以支持复杂跨GPU预测器。先不开发新的选择算法。

同一形状、同一进程下，四种模式共享输入、打包权重、输出、workspace和显式侧流；V7使用同一打包权重的门控/上投影视图。

| 模式 | 计时区间内的路径 |
|---|---|
| python_binding | Python Event + 既有完整张量校验/ctypes绑定 |
| python_raw | Python Event + 预绑定函数与参数，不重复张量校验 |
| native_eager | C++内部Event、原导出函数调用与同步；没有Python夹在开始/结束事件之间 |
| native_graph | C++内部Event和单次CUDA Graph重放；图只包含一次同样算子工作 |

native_eager仍有cuBLAS/CUDA主机提交工作，不是纯设备计算真值。native_graph不是把32次取均值当单请求延迟。
原始直接调用只用于实验，不对外提供绕过校验的新生产接口。

## 结果二：模型维度探针不支持复杂选择器的必要性

图重放时延，单位微秒：

| MxKxN | 进程 | V4 cuBLAS | V7自定义 |
|---|---|---:|---:|
| 16x1536x8960 | run01 | 38.912 | 46.096 |
| 16x1536x8960 | run02 | 121.856 | 284.928 |
| 128x1536x8960 | run01 | 108.408 | 311.424 |
| 128x1536x8960 | run02 | 148.736 | 460.072 |

这四组图模式均支持V4超过5%优势。16x1536x8960的C++普通模式第一进程未决、第二进程V4获胜；不把第一进程单次中位数差异写成V7收益。
在这些代表维度上，固定cuBLAS是足够强的现有候选。还没有同语义torch.compile完整模块基线，不能宣称打败或覆盖它。

两进程的绝对时间在模型维度上明显漂移（尤其M16），这是局限而不是新优化结果。运行前后快照SM频率均报告2385MHz，但粗快照无法排除瞬时频率、外部图形负载、缓存或其他状态变化；不能指定唯一原因。

## 构建失败、修正与测试

本批先出现辅助库构建问题：使用CUDA12.8 nvcc但默认--cudart shared误找到系统libcudart.so.11.0；两次smoke在图捕获时进程崩溃，没有产生任何正式比较组。
随后改为显式匹配PyTorch CUDA12运行库，并拒绝不匹配的ELF依赖。首次把.so.12作为nvcc输入失败，最终用--cudart=none、-L和-l:libcudart.so.12正确链接。
没有修改系统CUDA路径、安装依赖或替换生产库。失败构建/崩溃日志与错误辅助库仍保留，不删掉不利记录。

## 统计和归因限制

- 每种模式内候选配对交错；不同模式按分组随机顺序执行，不是严格同步相同状态的逐样本跨模式配对。因此不能用模式之间的差直接量化唯一的Python成本。
- Python与native墙钟边界不相同，原始墙钟用于诊断，不做精确CPU开销相减。
- 多个轮次中位数落在离散计时格点，bootstrap区间可能退化为一点；这不是零噪声或形式化保证。
- 单卡、两个候选、合成随机权重、自然热复用、未锁频、无跨日验证，不宣称普适GPU规律。
- 本批没有完整BF16前馈、torch.compile强后端、真实流量权重、在线策略查询或重新校准摊销实验。
